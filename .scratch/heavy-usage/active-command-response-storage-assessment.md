# Independent assessment: active command-response storage

Date: 2026-11-01. Scope: ticket 07, assessment only. Sources are checked-out repository code, domain/architecture documents, ADRs and tests. The only executed experiment imports Node built-ins and generates synthetic in-memory objects. No retained project state, live/backup database, host, runtime API or production code was used or modified. Tests cited below were inspected, not executed.

## Verdict

Compact durable operation receipts are a good strategic answer **if the project deliberately simplifies the application command-result contract**. They are not a transparent storage replacement for today's exact full application responses. IDs and revisions plus fresh hydration cannot reproduce those responses. A receipt must retain the original compact response facts, not merely enough IDs to look up current state.

The actual browser product flows make that contract simplification proportionate: creation needs only the created task ID; comments, edits, movement, relationships and lifecycle controls refresh authoritative reads after successful commands. Keeping growing task histories inside command results supplies little leverage to those flows. The agent transport already exposes compact results. Therefore I favor a specified compact application result for the growing task mutation families, with durable request matching and historical compact replay, over retaining rich snapshots forever. This is a recommendation for a decision, not authorization to change the contract.

If exact existing application/browser response objects must remain supported, choose lossless response compression instead. It localizes the change and preserves that requirement, although it does not solve the underlying repeated-history growth. Do not build compression as a mandatory precursor to receipts if the compact contract is accepted; that would introduce two storage transitions where one may suffice.

The Technical Designer guidance calls for proportionate design and distinction between hypotheses and requirements; the Code Reviewer guidance explicitly weighs complexity against practical consequences. That argues against either rubber-stamping receipts as invisible or treating every currently returned, unused field as a permanent product requirement. Repository workflow requires specification and dependency-aware delivery tickets after the decision; the parent owns those tracker changes, and this document does not claim delivery completion.

## Existing authority, identity and retention

The command workflow transaction and shared `IdempotentCommandExecutor` are the right seam. `execute` checks normalized request JSON, replays an existing response before running the operation, and retains the result under the workflow's policy in the same transaction ([executor](../../src/application/internal/idempotent-command-executor.ts:54), [ADR 0009](../../docs/adr/0009-share-transaction-bound-coordination-write-mechanics.md:5)). A storage codec can remain inside this deep module. Compact result meaning belongs to the command workflows; a persistence module should not guess arbitrary generic result shapes.

Identity is `(serialized command type, idempotency key)`, not the key alone. Legacy identities are colon-delimited kind/scope strings; caller-aware identities are JSON `[kind, caller, scope]` ([executor](../../src/application/internal/idempotent-command-executor.ts:94)). Edit/move/comment scopes name the origin task for cross-task callers; caller identity includes actor kind/ID. Creation and relationships include origin/source task in their caller tuple ([task commands](../../src/application/internal/task-command-store.ts:69), [edit](../../src/application/internal/task-command-store.ts:140), [comments](../../src/application/internal/task-command-store.ts:583), [relationships](../../src/application/internal/task-command-store.ts:360)). Browser and agent provenance must remain distinct. Attempt identity is not part of these keys; adding it would let the same intended operation execute again after runtime retry. Authentication/provenance validation still applies at its existing entry points; replay durability does not grant an ended agent attempt new authorization.

`request_json` is not a second cache of the response. It supplies normalized target/payload equality, including `expectedRevision`, selected target, comment text and pin intent ([edit request](../../src/application/internal/task-command-store.ts:203), [comment request](../../src/application/internal/task-command-store.ts:645)). Some values duplicate retained authored sources, but those sources do not encode the whole request or all historical normalized intent. Keeping requests is linear under bounded requests. Removing them loses changed-payload rejection; replacing them with only a hash introduces a collision assumption and loses exact request evidence. Start with existing exact normalized strings. Compressing requests losslessly later is a separate optional optimization. Preserve NULL semantics on legacy rows: a row without matching retained request evidence must not silently gain permission to replay a changed request.

Archival is the existing explicit expiry boundary. It removes provably task-owned ordinary mutation responses atomically, preserves creation/child creation/archive/unarchive/bulk receipts, and retains unknown/unscoped identities conservatively ([retention](../../src/application/internal/command-response-retention.ts:4), [archive call](../../src/application/internal/task-archive-store.ts:195), [ADR 0034](../../docs/adr/0034-expire-task-owned-command-responses-at-archival.md:21)). Cross-task response ownership follows the caller, not the destination. Active receipts should initially keep this policy. Retaining compact tombstones beyond archival could improve duplicate protection, but would change the already accepted post-archive retry window; do not introduce it accidentally.

Neither context compaction nor conversation retirement proves retry identity can be forgotten. Context-fill measures current thread occupancy rather than cumulative usage ([CONTEXT](../../CONTEXT.md:193), [ADR 0015](../../docs/adr/0015-adapt-codex-rollout-context-usage.md:5)). Retirement leaves a conversation readable and explicitly continuable ([CONTEXT](../../CONTEXT.md:201)); ordinary command keys do not include its conversation/thread identity. A stale caller, lost response, restored client or retry after restart can still reuse the key. Composition checkpoints describe delivered task context, not command acknowledgments ([ADR 0021](../../docs/adr/0021-page-whole-history-records-at-conversation-checkpoints.md:12)). No source establishes a safe active-task TTL or size-based eviction rule.

Keep small existing control results small. |

Exact current replay cannot be reconstructed from task ID/revision: full projection reads comments, events, activations and mutable relationship information ([projection](../../src/application/internal/task-projection-store.ts:83)). Comments do not increment the task revision; existing concurrency coverage asserts this ([test](../../test/application/concurrency-control.test.ts:173)). Later comments therefore change the full snapshot without changing revision. Pin state, activation settlement, task title and relationship metadata can also change. The synthetic experiment demonstrates the first counterexample without accessing a database.

Existing tests explicitly compare repeated application results ([cross-task tests](../../test/application/cross-task-mutations.test.ts:118), [move/create](../../test/application/cross-task-mutations.test.ts:199), [conversation](../../test/application/agent-conversation.test.ts:329)). Others inspect command-returned activations/history ([activation test](../../test/application/task-activation.test.ts:146)). Those tests should move historical read assertions to authoritative queries only after the command interface has been deliberately changed; merely deleting assertions would conceal a regression.

Historical failure handling needs its own rule. Current edit/move/comment/relationship commands retain accepted results only, so an ordinary new revision-conflict response is not cached ([edit policy](../../src/application/internal/task-command-store.ts:203)). Other executor call sites use its default retain-all policy ([attention](../../src/application/internal/task-command-store.ts:725), [activation resolution](../../src/application/internal/activation-resolution-module.ts:111)); archival explicitly retains rejections ([archive](../../src/application/internal/task-archive-store.ts:85)). Existing durable rows must not be assumed to contain only current success shapes. A historical failure with `currentTask` must either preserve its historical compact fields under the accepted new contract or remain as an exact legacy payload. Never recompute an old failure against current state or convert an unrecognized retained failure into a fresh operation.

## Growth and isolated measurement

Let `n` be retained mutation responses for one active task. Assume bounded command payloads, a bounded number of appended comments/events/attempt facts per command, and no recursive embedding of command responses inside source history. If response `i` includes history of size `H0 + b*i`, total response bytes are `n*H0 + b*n*(n+1)/2 = Θ(n²)`. At fixed small request/receipt size, receipts plus normalized requests are Θ(n). Across tasks sum each task's sequence (cross-task relationships can include two histories). Large authored inputs, independently growing attempt history or deliberate copying of old text violate the bounded-size assumptions; there is no evidence here for an intrinsic exponential recurrence. Full responses are not themselves automatically embedded in `TaskView`.

Lossless per-row compression may substantially reduce bytes, but no linear bound follows: each independently compressed response may still contain all earlier unique history. It also leaves full projection construction/serialization work and synchronous decompression CPU. Highly repeated text can compress better than unique authored content; runtime transcripts and real corpus distributions were not sampled.

Run `node .scratch/heavy-usage/response-storage-synthetic.mjs`. It generates 512-character deterministic hash-derived comment bodies and one response after each append; compares raw JSON, per-response gzip level 6, Brotli quality 4, and a deliberately smaller receipt. All variants include unchanged normalized request bytes. It asserts exact decompression round trips and the same-revision replay counterexample.

| Commands | Current response + request bytes | Gzip response + request bytes | Brotli response + request bytes | Receipt + request bytes |
| ---: | ---: | ---: | ---: | ---: |
| 100 | 3,253,535 | 1,533,479 | 1,469,630 | 61,390 |
| 200 | 12,692,185 | 5,959,721 | 5,687,932 | 122,890 |
| 400 | 50,139,485 | 23,484,157 | 22,463,107 | 245,890 |
| 800 | 199,314,085 | 93,226,547 | 89,771,963 | 491,890 |

These are **synthetic payload counts, not production savings**. They omit SQLite pages/indexes, identity keys, WAL, backups, compression envelopes and CPU/latency; the receipt is an intentionally simplified comment result rather than a proposed universal schema. Approximately fourfold raw/compressed totals versus twofold receipt totals under doubling illustrate this fixture's growth. No storage codec is guaranteed to achieve the measured compression ratios on production text.

## Alternatives and proportionality

1. **Compact command result plus receipt (recommended if contract change accepted).** Store original scalar facts/compact immutable result and exact normalized request; read rich current state separately. Removes growing histories from both persistence and command projection work. Requires coordinated application/browser contract and tests, careful historical conversion, and an ADR superseding the active full-response clause of ADR 0034. Do not introduce an elaborate generic event-sourcing scheme merely to keep unused return fields.
2. **Lossless exact-response compression.** Encode original serialized bytes using a versioned codec; preserve old plain JSON reads. Small interface/consumer impact, useful if exact snapshots are required or an urgent storage reduction must precede contract work. Prefer BLOB storage for compressed bytes; base64-in-TEXT adds encoding overhead. Compression threshold and plain fallback avoid enlarging tiny receipts. Detect corrupt/unknown codecs as errors, never cache misses. Does not remove repeated historical content or full projection cost.
3. **Normalized/deduplicated immutable snapshot representation.** Retain historical scalars plus immutable references/chunks with persistent sequence structure, or carefully bounded deltas/checkpoints. Can preserve full replay while sharing repeated histories. More complex integrity, reference lifetime, deletion, decode and migration behavior; simple deduplication of whole response blobs misses nearly all successively changed snapshots. Not proportionate without a demonstrated requirement for full historical replay and growth beyond compression's acceptable horizon.
4. **TTL/LRU/count eviction or clear-on-compaction/retirement.** Cheap space reduction but loses duplicate protection for valid old keys and cannot replay original creation/lifecycle outcomes. Reject without an explicit new expiry/acknowledgment protocol. Archival already supplies a documented narrower boundary.
5. **Receipt plus fresh `TaskView` hydration.** Protects effects but silently changes replayed historical metadata and rich response. Reject as an invisible implementation change; only legitimate as a separately documented current-state response contract, with original mutation facts clearly separate.

## Migration and delivery slices

Migration 0013 rewrites attribution inside plain response snapshots and creates canonical-human command-key aliases while keeping legacy keys ([migration](../../src/application/internal/migrations/0013-canonical-human-identity.ts:24)). Append a new migration; never edit released history. A database upgrading from before 0013 must execute its normalization/aliasing before new encoding/conversion. Preserve both keys, each original request value and existing collision behavior (`INSERT OR IGNORE`); do not assume aliases can be removed. Deduplicating their payload storage is optional and should not complicate the first delivery.

Use the released migration registry and checked-in current-schema snapshot, transactional migration, verified pre-upgrade backup and schema/integrity/foreign-key checks ([ADR 0018](../../docs/adr/0018-make-released-migrations-the-coordination-schema-authority.md:5)). Iterate rows rather than loading all giant snapshots simultaneously. Budget old payloads, new payloads, rollback/WAL and backup disk space; reducing logical bytes need not shrink the database file until separately controlled compaction. Existing archival selection should continue reading keys only. Existing creation/lifecycle rows remain protected even if their result format becomes compact.

Suggested dependency-aware slices for the parent to publish, pending the user's strategy decision:

1. **Contract/specification decision.** Enumerate each command's original compact response, failure/retain policy, normalized request and owner; document intentional removal of rich application/browser mutation fields and agent-wire compatibility. Specify historical failure fallback and archive expiry. Acceptance: every serializer/consumer above mapped; no claim of exact old full-object compatibility. If that removal is unacceptable, select compression and retain existing contracts instead.
2. **Compact contract and durable receipts, depending on 1.** Update workflows, application/browser contracts, adapters and affected tests coherently. Retain original compact task/relationship/transition facts; do not read current mutable records for replay. Keep small conversation/control results as their current durable values where no growth problem exists. Acceptance: same key replays original facts after later comments, title/column changes, relationship edits/removal, pins, restart and authorized runtime retry; changed normalized request conflicts; another caller/operation scope remains independent; duplicate mention/notification/activation effects occur once; transaction rollback stores neither effect nor receipt. UI creation, edit, comment, move/conflict, relationships and lifecycle flows still refresh and navigate correctly. Agent HTTP/MCP fields/status remain stable.
3. **Existing-row upgrade/maintenance, depending on 2** (may be one release with 2). Convert only proven supported response shapes, retaining versioned exact fallback for unknown legacy/failure rows; preservation is safer than dropping keys. If current full application exact replay remains required for legacy rows, retain those snapshots explicitly and acknowledge that historical storage stays until compressed/expired. Acceptance: synthetic old-prefix upgrades including pre-0013, canonical/legacy aliases and collisions, NULL requests, retained failures/currentTask, unscoped keys, two-endpoint relationships, creation after archive and old unarchive retries; archival owner policy unchanged; failed conversion rolls back and verified backup restores; no silent re-execution on decode error. Document offline compaction as an operational step, not automatic vacuum on commands.
4. **If selected instead: exact codec delivery, depending on compression specification.** Localize versioned read/write coding to the executor and adapt direct migration readers. Acceptance: byte-for-byte decompression and parsed-object replay equality for success/failure/currentTask, plain/encoded mixed histories, restart, alias upgrades, corruption rejection, threshold behavior, atomicity and unchanged archive selection. This is an alternative path, not a compulsory receipt prerequisite.

Do not make these slices contingent on real idle-game experimentation. Synthetic fixtures and application-interface tests can establish correctness. Production size/latency inspection, if later explicitly authorized, should inform capacity expectations rather than retroactively turn this fixture into measured production benefit.
